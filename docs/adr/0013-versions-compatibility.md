# ADR 0013 — Versions, migrations and compatibility

Status: Accepted — 2026-10-24

## Context

One binary (0003). Its contracts are external protocols defined by others (Nix, Go, Cargo, Hex, npm), the configuration generated by its own module, and its on-disk state.

## Decision

- **Single semver `0.x` version** of the Cargo workspace; a release is a commit with the bump and a signed tag `vX.Y.Z`.
- **Schema migrations**: forward-only, numbered, embedded, applied at startup inside one transaction (`PRAGMA user_version`); `oroshi gc` refuses to run against a database of another version. No downgrade: rolling back past a migration means restoring a dump (primary data, 0004) or starting the cache empty (cache data).
- **Blob layout** carries its version in `stateDir/LAYOUT` (`1`); a binary that does not know it refuses to start.
- **Protocol compatibility** is defined by the client versions in the flake's nixpkgs, exercised by the nixosTests (0012). A protocol feature a newer client needs is a change with a test, never a silent extension.
- **Configuration**: the module and the binary ship together; an option removed or renamed fails `config check` at build time (`deny_unknown_fields`), never at runtime.

## Consequences

- A cache can always be dropped and refilled; only primary data needs a backward story, and it gets its backup ADR with the first module that stores it (O4).

## Rejected alternatives

- Reversible migrations: a permanent cost for a rare case.
- Per-module versions: one binary, one release.
